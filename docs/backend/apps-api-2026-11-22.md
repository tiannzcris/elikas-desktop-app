# API changes for the mobile and desktop apps (November 22, 2026)

This covers every API change from the November 22 work (three batches:
the first fixes, the page-by-page changes, and the barangay official's
pages with volcanic events). Paths are relative to `/api/v1`. Responses
keep the usual envelope `{success, message, data, errors}`.

The list of what the apps have to change is at the end.

The second November 23 update (sign-in by username, temporary passwords,
locked accounts, maintenance mode, device headers, Report a problem, system
notices, final counts submitted on behalf, paper EC Board totals) is in
`docs/apps-api-2026-11-23.md`.

## 1. Events, the selected event, and locks

### The selected event

- Every event-based read uses the user's selected event
  (`GET /selected-event`, `PUT /selected-event {evacuation_event_id}`),
  unless the request names `evacuation_event_id`.
- A barangay official's default event at login: an Active event, else a
  Monitoring one, then the newest start date, then the highest id. It is
  reset to this default at every login.
- `api/v1/public/*` never uses a signed-in user's selected event. With
  `ELIKAS_PUBLIC_SHOW_DEMO=true`, demo events count and show like normal
  events on the public pages.
- `GET /evacuees` accepts an optional `evacuation_event_id` and searches
  that event only.

### Locks: what is refused, and the 422 messages

Changes that belong to an event are checked by one rule for the web and
the apps. The refusal is a 422 with the message in `message` and in
`errors.evacuation_event_id`.

| When | Message |
| --- | --- |
| The event is **closed** | `"<event name>" is closed. A closed event is read-only.` |
| Registering while **no event is open** | `No open event yet. CSWDO opens an event when a threat is announced.` |
| The event is **monitored** and the action waits for the evacuation | `"<event name>" is being monitored. <What> opens when CSWD starts the evacuation.` |

`<What>` is one of: Registering evacuees, Registering returning families,
The EC Board, Registering families in private houses, Checking in listed
families, Relief rounds, Dispatching relief boxes, Handing out relief
boxes, Transfers, Final counts, DROMIC reports, Final reports, EC
Information Boards.

### Start evacuation, Families are arriving

- `POST /evacuation-events/{id}/start` (CSWD, `events.manage`):
  monitoring becomes active. Every barangay official gets a
  `RegistrationOpen` notification. Recording a Preemptive or Forced order
  (`POST /gis/barangay-status`) notifies that barangay's officials the
  same way.
- `POST /evacuation-events/{id}/families-arriving {note?}` (officials,
  while monitored): CSWD is told. Nothing else changes.
- `GET /evacuation-events/{id}/status-summary` (CSWD): the figures for
  one event, and what closing would leave behind (`close_check`).

### Practice events (demo events) look like real events (November 23)

The demonstration events are now named and shown like real ones, so a
demonstration looks real. They are told apart only by `is_demo`.

- `demo:reset` seeds two practice events: **"Typhoon Drill"** (active)
  and **"Incoming Typhoon"** (monitoring). There is no made-up closed
  event any more ("DEMO - Past Typhoon" is gone). The past events of a
  demonstration are the real closed ones (Opong, Ramil, Uwan, Mayon).
- A demo event's name no longer starts with `DEMO - `, and the server no
  longer adds that prefix (also not when an event is renamed or marked
  with `demo:mark`). Never look at the name to decide anything.
- Their families, members and puroks have realistic fictional names
  ("Maria Santos", "Purok 1"). Notes, reasons, orders and reference
  numbers have no "DEMO:" text.
- `is_demo` is still on every event (`GET /evacuation-events`,
  `/selected-event`, `/evacuation-events/{id}/summary`, the dashboard,
  map and monitoring `evacuation_event` objects). Use it **only for
  internal logic**: leave the event out of history, past events,
  forecasts and accuracy, never offer a CDRRMO final report for it, show
  the two practice actions below for it only.
- **Hide the DEMO badge.** Show no DEMO badge, label, colour or "(demo)"
  text anywhere: event lists, the event switcher, headers,
  notifications. The web app shows none.
- Unchanged: DROMIC and EC Information Board files generated for a demo
  event (including the DROMIC review draft) are named
  `DEMO-not-for-submission_...xlsx` and open on a "DEMO – not for
  submission" sheet. Keep the file name as the server sends it.
- The 422 message for a CDRRMO final report of a demo event is now
  `This is a practice event with made-up data. The CDRRMO final report is
  not generated for it.`

### Practice-event tools (CSWD, demo events only)

- `DELETE /evacuation-events/{id}/demo {confirm_name}` and
  `POST /demo/reset` now answer **202** at once and run in the
  background. While one runs, `GET /demo/status` returns
  `{demo_task: {task, label, started_at, by}}`, otherwise
  `{demo_task: null}`. A second start while one runs gets **409**. The
  user who started it gets a `DemoTaskFinished` notification.
- Label them **"Delete practice event"** and **"Reset practice events"**,
  and offer them only for an event with `is_demo: true`. The server's
  texts now say "practice event": `label` is "Resetting practice events…"
  or "Deleting <name>…"; the notification titles are "Practice event
  deleted", "Practice event not deleted", "Practice events reset" and
  "Practice events not reset".

### Volcanic events (new fields)

On every event (`GET /evacuation-events`, `.../{id}`), set by CSWD with
`POST` or `PATCH /evacuation-events/{id}`:

| Field | Type | Notes |
| --- | --- | --- |
| `phivolcs_alert_level` | integer 0-5, nullable | From PHIVOLCS. The system never detects an eruption. |
| `phivolcs_bulletin_url` | URL, nullable | Link to the PHIVOLCS bulletin. |
| `live_video_url` | https URL, nullable | Optional. Show it as "For reference only. Official alerts come from PHIVOLCS." |

For a volcanic event (`event_type = volcanic_eruption`):

- There is **no forecast**. Every forecast field is `null`. Show "No
  forecast for volcanic events yet. Plan using the barangays inside the
  danger zone."
- `GET /volcano` (operational access) returns:
  - `evacuation_event`: the selected event, with `is_volcanic` and the
    three fields above.
  - `zones`: `{permanent_km: 6, extended_km: 7, buffer_km, label}`. Show
    `label` with every zone: "Approximate zone based on distance from the
    summit. Follow PHIVOLCS bulletins."
  - `barangays`: each one Inside or Near, with `status`, `nearest_km`,
    `to_extended_km`, `pct_permanent`, `pct_extended`, and (once Active)
    `registered_families`, `now_persons` and `list`.
  - `centers_inside`: centers within 7 km, each with
    `warning: "Inside the danger zone. Do not use."`.
  - `safe_centers`: open centers outside the zones and the buffer, the
    most room first.
- Treat a center as inside a danger zone when it is within 6 km of the
  summit (13.2570 N, 123.6856 E), always. During a volcanic event, also
  within 7 km. Warn before registering anyone there.
- `GET /transfer-requests/suggestions` leaves out centers inside the
  zones during a volcanic event.

## 2. Evacuation centers

- **Pending centers.** While the event is Active, a barangay may register
  evacuees at its own center that is still waiting for approval. The
  center's rows carry `pending_warning: "Pending CSWD approval"`. The
  first evacuee there sends CSWD an urgent notification
  (`GET /notifications` rows have `urgent: true`). Rejected centers stay
  unusable, and so do pending centers while the event is monitored.
- **Map location.** `POST /gis/centers/{id}/location {latitude, longitude}`
  now needs the new permission `centers.set_location`, which CSWD and
  officials both have.
  - An official sets the location of their own centers. For an approved
    center this goes to approval (202), as before.
  - CSWD can set or move the location of any center. It is saved at once
    (200) and logged.
  - `GET /gis/centers/{id}` returns `can.set_location`.
- **Your submissions** (officials):
  - `DELETE /evacuation-centers/{id}/submission` withdraws a center still
    waiting for CSWD, or deletes a rejected one.
  - `POST /evacuation-center-change-requests/{id}/withdraw` withdraws an
    edit still waiting.
  - Both return 422 for an approved center or for a center where
    families were ever registered.
- **The CSV capacity import is removed:** `POST
  /evacuation-centers/capacity-import` and the permission
  `centers.import_capacity` no longer exist. Official capacities come
  from barangay edits that CSWD approves.
- **The GIS map for officials.**
  - `GET /gis/map-data` returns every approved center of the city for
    officials too: name, status, people inside and capacity, never who is
    inside. Each feature now has `barangay_id`.
  - `GET /gis/situation` lists every barangay for officials. Another
    barangay's row is read-only: `read_only: true`, `may_update: false`,
    and only the status, label, rank and `set_at`.
  - `GET /gis/barangay-hazards` gives "Your barangay": `flood`
    (`very_high_pct`, `high_pct`, `high_or_very_high_pct`) and `mayon`
    (distances and shares of area, as in `/volcano`). CSWD passes
    `?barangay_id=`.
- **Statuses.** Normal, Watch and Flooding are marked by the barangay's
  own official. CSWD marks them only for a barangay with no official.
  Otherwise CSWD uses `POST /gis/barangays/{id}/ask-update`, which
  notifies the barangay's officials. CSWD still records evacuation orders
  and lifts them.

## 3. Families to evacuate (new)

A barangay's list of the families it expects to move in an event, per
purok. **A listed family is not an evacuee.** It is never in a total, a
final count, DROMIC or relief, until it is checked in.

| Method | Path | Who | Notes |
| --- | --- | --- | --- |
| GET | `/families-to-evacuate` | operational access | The selected event (or `?evacuation_event_id=`). Officials get their own barangay; CSWD gets every barangay, or `?barangay_id=`. Returns `summary {families, persons, checked_in}`, `can {manage, check_in}` and `families`. High-risk puroks come first. |
| GET | `/families-to-evacuate/past-families?search=` | officials | Families of the barangay from past (closed) events that can be picked, one per household. |
| POST | `/families-to-evacuate` | officials | `evacuation_event_id`, plus either `source_family_id` (reuse a past record: head and members come from it), or `head_first_name`, `head_last_name`, `head_sex?` and `members_count` (1-30). Optional: `purok_id`, `contact_number`, `note`. Allowed while the event is monitored or active. |
| PATCH | `/families-to-evacuate/{id}` | officials | While the family is still `expected`. |
| DELETE | `/families-to-evacuate/{id}` | officials | While the family is still `expected`. |
| POST | `/families-to-evacuate/{id}/check-in` | officials, **Active only** | `evacuation_center_id` (one of the barangay's own centers), or `host_name` (plus `host_purok_id` or `host_address`) for a private house. **Send `client_ref`** (a UUID); a retry returns the first answer. Returns `registered_family_id`. Named members of a past family are copied (names, sex, birthdates, sectors). The rest of `members_count` is added without names, to complete later. |

Row fields: `id`, `head`, `head_first_name`, `head_last_name`,
`head_sex`, `members_count`, `purok {id, name, is_high_risk, risk}`,
`barangay`, `contact_number`, `note`, `from_past_event`, `status`
(`expected` or `checked_in`), `family_id`, `checked_in_at`.

New permission: `families_to_evacuate.manage` (officials).

"X of Y listed families checked in" appears as a `list` object
(`{families, persons, checked_in}`, or `null` when the barangay listed
none) on:

- the barangay rows of `GET /dashboard/city`
- the barangay rows of `GET /monitoring/evacuees`
- the barangay rows of `GET /box-relief/overview`
- `GET /dashboard/barangay`

## 4. Puroks

- `PATCH /puroks/{id}` also takes `high_risk_flood` and/or
  `high_risk_landslide` (booleans) on their own. The purok rows return
  both, plus `is_high_risk`.
- `families_count` is the number of family records naming the purok,
  across every event ("Families on record").
- Adding a purok is never locked by an event.

## 5. Facility requests

The flow is Waiting → Approved → Sent → Received, or Rejected.

- `POST /facility-requests/{id}/approve {quantity_approved?, note?}`:
  approving fewer than asked needs a note ("Approved 6 of 10").
- `POST /facility-requests/{id}/send` (CSWD), then
  `POST /facility-requests/{id}/receive` (the center's barangay).
- `POST /facility-requests/{id}/fulfill` is **deprecated**, but still
  works for the installed apps. It marks an approved or sent request as
  Received, and the response carries `Deprecation: true`. New code uses
  `send` and `receive`.
- `status` values are `pending`, `approved`, `sent`, `received` and
  `rejected`. `fulfilled` is gone (old rows became `received`).
- Requests carry `unit`, `quantity_approved`, `sent_by/at`,
  `received_by/at` and `context`. The create body also takes `unit`.
- `GET /facility-requests/suggestions` (officials): what each center is
  short of by the planning standards for a full center, minus what is
  already asked. Each row is ready to send as a request.

## 6. Relief boxes

- **Need.** A barangay's need is its validated count, or its registered
  count until a count is validated. Boxes can go out before validation.
  The overview has `need_basis` (`validated` or `registered`),
  `registered_now` and `validated` per barangay.
- **Families staying in another barangay.** The box comes from the
  barangay where the family stays (the host).
  - The host's families list has `from_barangay {id, name}` (the home
    barangay) and `purok: null` for such a family.
  - The home barangay cannot give it a box (403).
  - The handout's barangay is the host.
  - The box need moves to the host. Reports still count the family under
    its home barangay.
  - See docs/box-relief-transferred-families.md.
- **While the event is monitored**, `GET /box-relief/barangay` returns
  `plan {forecast, list, round_1_boxes, round_1_basis}`. Round 1 is one
  box per family: the list or the high end of the forecast, whichever is
  more.

## 7. Final counts, transfers, the dashboards

- **Final counts.** `POST /barangays/{id}/remind-final-count` (CSWD)
  notifies the barangay's officials. A barangay with a validated count and
  nothing new has nothing to submit, and the web disables "Submit updated
  count".
- **Transfers.** `GET /transfer-requests`: `from_center` and `to_center`
  carry `occupancy`, `capacity_persons`, `capacity_source`, `room_left`
  and `status`; `to_center` also has `lacks_room`. `counts` has
  `pending`, `accepted`, `declined` and `all`.
- **`GET /dashboard/barangay`** now adds:
  - `plan {forecast, space, centers_ready}`, while the event is not
    closed.
  - `list`
  - `readiness` on each center.
  - Facility requests with `unit`, `quantity_approved` and `may_receive`.
  - A fuller `todo`: capacity, map location, facilities checklist, and
    supplies short, each with an `action`.
  - `status.may_say_arriving`
  - `alerts`, which leaves out archived alerts and alerts meant for
    another barangay.
- **Monitoring for officials.** The web's official Monitoring page is now
  part of My barangay. `GET /monitoring/{section}` is unchanged for the
  apps.

## 8. Alerts

- **Levels.**
  - **Emergency** (`severity: mandatory`) is always sent by SMS to the
    barangay officials.
  - **Advisory**: SMS is optional.
  - **Info**: never sent by SMS.
- **Target.** Send `barangay_id` to target one barangay. Each alert
  returns `target {kind, label}`, `channels` and `archived_at` (staff
  only).
- **Archive.** `POST /alerts/{id}/archive {unarchive?}` (CSWD). Archived
  alerts are hidden from lists and the public. A **sent alert can no
  longer be deleted**: `DELETE /alerts/{id}` returns 422 "A sent alert
  cannot be deleted. Archive it instead."
- **What officials see.** `GET /alerts` returns only sent alerts for the
  whole city or for their own barangay: no archived alerts, drafts,
  alerts for one person, or other barangays' alerts.

## What the apps must change

1. **Locks.** Show the 422 message as it comes. While an event is
   monitored, registering, the EC Board, relief, transfers, final counts
   and reports wait for "Start evacuation".
2. **Facility requests.**
   - Replace "Mark fulfilled" with CSWD "Mark sent" and the barangay's
     "Mark received". `fulfill` still works for now, but it is deprecated
     and will be removed.
   - Read the statuses `sent` and `received`.
   - Show `unit` and "Approved 6 of 10".
3. **Alerts.**
   - Drop "Delete" for sent alerts and use Archive.
   - Use the three levels (Emergency always SMS, Info never).
   - Officials: show only what `GET /alerts` returns.
4. **Capacity import.** Remove any capacity CSV import screen. The
   endpoint is gone.
5. **GIS statuses.** An official marks Normal, Watch and Flooding for
   their own barangay. CSWD asks instead
   (`POST /gis/barangays/{id}/ask-update`), unless the barangay has no
   official. Other barangays' statuses are read-only for officials.
6. **Map locations.** Use `can.set_location`. CSWD can set any center's
   location, saved at once.
7. **Families to evacuate.**
   - Add the list for officials (monitoring and active).
   - Check in with one tap and a `client_ref`.
   - Never count listed families as evacuees.
   - Show "X of Y listed families checked in" to CSWD from the `list`
     objects.
8. **Pending centers.** While the event is Active, allow the official's
   own pending center, show "Pending CSWD approval", and expect the
   urgent notification.
9. **Relief.**
   - Show the need basis ("based on registered count, not yet
     validated").
   - A family staying in another barangay is given its box by the host,
     with "From <barangay>".
10. **Volcanic events.**
    - Show the PHIVOLCS Alert Level and the bulletin link.
    - Show no forecast.
    - Show the zones with their label.
    - Warn on centers inside a zone ("Inside the danger zone. Do not
      use.").
    - Use `GET /volcano`.
11. **Practice events (demo events).**
    - Hide the DEMO badge and any DEMO label everywhere; a practice event
      looks like any other event.
    - Use `is_demo` only for internal logic (history, forecasts, reports,
      which actions to offer), never the event name.
    - Label the actions "Delete practice event" and "Reset practice
      events". `DELETE .../demo` and `POST /demo/reset` answer 202; poll
      `GET /demo/status` until it returns `demo_task: null`.
12. **Puroks.** Show and set the High-risk marks (flood / landslide).
