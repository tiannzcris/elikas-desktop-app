# API for the mobile and desktop apps (November 24, 2026)

The answers to the gaps the mobile app (0.4.0) and the desktop app (2.1.0)
found. Paths are relative to `/api/v1`. Responses use the usual envelope
`{success, message, data, errors}`. Every example below is a real response
from the code, captured in a test, with the names changed to read like a
real barangay. Section 9 lists what each app must change.

Every change here adds to the API. No field was removed or renamed, and a
request that worked before still works the same way.

Sign-in, the device headers (`X-Device-Id`, `X-App-Version`,
`X-App-Platform`), maintenance mode and temporary passwords work as in
`docs/apps-api-2026-11-23.md`. The `client_ref` rules are in
`docs/client-ref-api.md`; section 0 repeats them in brief.

## 0. client_ref in brief

`client_ref` is a UUID the app makes once per queued record and sends with
every try, in the JSON body beside the other fields.

| Case | Answer |
| --- | --- |
| First success | As usual (201). The answer is kept. |
| Same `client_ref` again (same user, same endpoint) | The kept answer: same status and body, header `Idempotent-Replayed: true`. Nothing new is created. Treat it as a success. |
| Refused (403, 409, 422) | Nothing is kept. Fix the request and send it again with the **same** `client_ref`. |
| Not a UUID | 422, `errors.client_ref` = `["client_ref must be a UUID."]` |
| Used before by another user or on another endpoint | 422, `errors.client_ref` = `["This client_ref was already used for another request."]` |

Endpoints that accept `client_ref` now:

| Method and path | Since |
| --- | --- |
| `POST /evacuation-centers/{id}/evacuees` | Nov 16 |
| `POST /evacuation-centers/{id}/re-enroll` | Nov 16 |
| `POST /families/register` | Nov 16 |
| `POST /barangays/{barangay}/private-house-families` | Nov 22 |
| `POST /families-to-evacuate/{id}/check-in` | Nov 22 |
| `POST /box-relief/rounds/{round}/handouts` (give one box) | **new** |
| `POST /families-to-evacuate` (add a family to the list) | **new** |
| `POST /file-downloads` (report a saved file) | **new** |

## 1. Relief boxes for a barangay official

One relief box per family per round. CSWD dispatches boxes to the
barangay, the barangay confirms what arrived, then gives the boxes to
families. An official always works on their own barangay. CSWD may confirm
and give on behalf of a barangay **with no active official**; those
records are marked `*_on_behalf: true`.

### 1.1 The family list for a round

`GET /box-relief/rounds/{round}/families`

| Query | Meaning |
| --- | --- |
| `order` | `priority` (default) or `name`. The order of the families inside each purok. |
| `barangay_id` | CSWD only (required for CSWD). An official always gets their own barangay; the value is ignored. |

Who may call it: officials (own barangay), CSWD (any barangay). The
administrator gets 403.

#### Top-level fields

| Field | Meaning |
| --- | --- |
| `figures` | The barangay's boxes in this round. `left_to_give` = received − given. A box can be given while `left_to_give > 0`. |
| `next_family_id` | The family to give to next in the suggested order, across the whole barangay; `null` when everyone has a box. |
| `order` | The order used inside each purok. |
| `puroks[]` | Named puroks by name, then the families with no purok (`purok: null`). These are the families **this** barangay gives a box to. |
| `staying_elsewhere[]` | **New.** The barangay's own families staying now in **another** barangay's center. That barangay gives their box, so this one cannot (`may_give: false`). Shown for information; they are not in `figures` or in `puroks`. Sorted by name. |

#### Fields of each family in `puroks[].families[]`

| Field | Meaning |
| --- | --- |
| `from_barangay` | `{id, name}` when the family belongs to another barangay and stays in one of this barangay's centers ("From Bay"). `null` for the barangay's own families. Such a family has `purok: null` here. |
| `location` | `inside_center`, `outside_center` (private house), or `null` when no stay is recorded. |
| `host_name` | Who the family stays with, for a private house; else `null`. |
| `staying_in` | **New.** Where the family stays now: `{barangay: {id, name}, center: {id, name} or null, private_house: bool, other_barangay: bool}`. `other_barangay` is `true` when that barangay is not the family's home (a family "From" another barangay). `null` when the family is not staying anywhere now (no stay recorded, or gone home). |
| `may_give` | **New.** Whether this barangay is the one that gives the family its box. Always `true` in `puroks`, always `false` in `staying_elsewhere`. It does not look at stock or at whether a box was given: use `can_give` for the button. |
| `priority_tier` | Suggested priority, 1 (first) to 4, or `null` for none. See the table below. |
| `priority_reason` | `infant`, `pregnant_or_lactating`, `pwd_or_senior`, `child_or_single_headed`, or `null`. |
| `priority_label` | `Infant`, `Pregnant / lactating`, `PWD / senior`, `Child- or single-headed`, or `null`. |
| `priority_order` | The family's place in the suggested order **within its purok** (1 = first), whichever way the list is sorted. |
| `next_in_line` | `true` for the one family whose id is `next_family_id`. |
| `higher_priority_waiting` | How many families of this barangay with a **higher** tier (a smaller number; "none" counts as 5) have no box yet in this round. `0` once the family has its box. |
| `can_give` | `true` when the family has no box yet in this round and `figures.left_to_give > 0`. |
| `given`, `handout_id`, `given_at`, `given_by` (`{id, name}`), `given_on_behalf` | The box given in this round (not voided). |
| `voided_handouts[]` | Earlier boxes to this family in this round that were voided: `{id, given_at, voided_on_behalf, voided, voided_at, voided_by, void_reason}`. |

Priority tiers (`App\Services\BoxRelief\HandoutPriority`):

| Tier | `priority_reason` | `priority_label` |
| --- | --- | --- |
| 1 | `infant` | Infant |
| 2 | `pregnant_or_lactating` | Pregnant / lactating |
| 3 | `pwd_or_senior` | PWD / senior |
| 4 | `child_or_single_headed` | Child- or single-headed |
| `null` | `null` | `null` |

#### Fields of each family in `staying_elsewhere[]`

`id`, `name`, `head_name`, `member_count`, `purok` (its own purok, `{id, name}` or `null`), `staying_in` (as above, with `other_barangay: true`), `gives_box` (`{id, name}`: the barangay that gives its box), `may_give: false`, `given` (whether that barangay has given it a box in this round) and `given_at`.

### 1.2 Give one box to one family

`POST /box-relief/rounds/{round}/handouts`

```json
{"family_id": 3, "client_ref": "3f2b8c1e-5d6a-4b7c-8e9f-0a1b2c3d4e5f"}
```

| Field | Rule |
| --- | --- |
| `family_id` | Required, an existing family. |
| `client_ref` | Optional, a UUID. **New**: accepted now. |

201:

```json
{
  "success": true,
  "message": "Box given.",
  "data": {
    "id": 1,
    "family_id": 3,
    "given_at": "2026-11-23T16:29:30+00:00",
    "given_on_behalf": false,
    "figures": {
      "need": 3, "dispatched": 3, "in_transit": 0, "received": 3, "given": 1,
      "left_to_give": 2, "short": 0, "can_dispatch": 0, "requested": 0, "can_request": 0
    },
    "higher_priority_waiting": 1
  }
}
```

`figures` are the figures of the barangay that gave the box.
`higher_priority_waiting` is counted **before** this box was given.

The same request sent again with the same `client_ref` answers the same
201 and body, with header `Idempotent-Replayed: true`. No second box is
given and the activity log gets one entry.

Errors:

| Status | When | Body (`message`, `errors`) |
| --- | --- | --- |
| 422 | The family already has a box in this round (and the request had no `client_ref`, or a new one) | `This family already got its box for Round 1.`, `errors.family_id` |
| 422 | Nothing received yet | `No boxes have been received for Round 1 yet.`, `errors.family_id` |
| 422 | All received boxes given | `All 3 boxes received for Round 1 have been given.`, `errors.family_id` |
| 422 | Family not in this round's event, or a legacy head count | `This family is not registered in this event.`, `errors.family_id` |
| 422 | `family_id` missing | `errors.family_id` |
| 422 | The event is monitored | `"<event>" is being monitored. Handing out relief boxes opens when CSWD starts the evacuation.`, `errors.evacuation_event_id` |
| 422 | The event is closed | `"<event>" is closed. A closed event is read-only.`, `errors.evacuation_event_id` |
| 422 | CSWD giving for a barangay that has an active official | `errors.barangay_id` = `["This barangay has an active official, who confirms and gives its boxes."]` |
| 422 | Bad or reused `client_ref` | see section 0 |
| 403 | An official giving to a family whose box another barangay gives (including their own family staying in another barangay's center) | `{"message": "You can only do this for your own barangay."}` |
| 403 | No permission (the administrator) | `You are not authorized to perform this action.` |

### 1.3 Out-of-priority confirmation

Giving out of the suggested order is **allowed**; the server never blocks
it and has no confirm flag. The app asks before sending, the same way the
web page does:

1. Before sending, read the family's `higher_priority_waiting` from the
   list (1.1).
2. If it is above 0, ask: title **Give a box to this family?**, message
   **`<n>` higher-priority families have not received a box yet.
   Continue?** (`family has` when n is 1), buttons **Give box** and
   **Cancel**.
3. On **Give box**, send 1.2 as usual. If it is 0, send without asking.

After the give, the response's `higher_priority_waiting` says how many
were skipped (counted before the box was given). Highlight the
`next_in_line` family's button (the web shows a "Next in line" badge).

### 1.4 Families staying in another barangay (transferred families)

*(This is `docs/box-relief-transferred-families.md`, updated with the new
fields.)*

A family can stay in a center of another barangay, after a transfer or
because its own centers are full.

**The rule**

- **The box comes from the barangay where the family stays.** That
  barangay sees the family in its list with `from_barangay` ("From
  Tuburan") and gives the box from its own confirmed boxes. The family's
  home barangay does not list it in `puroks` and cannot give it a box
  (403). The home barangay sees it in `staying_elsewhere` instead, with
  `gives_box` and whether it was given.
- **The need for boxes moves with the family.** For relief, the host
  barangay's need goes up by one family and the home barangay's goes down
  by one. CSWD therefore dispatches the box to where the family actually
  is.
- **Reports count the family under its home barangay.** Final counts,
  DROMIC and the evacuee figures do not change: the family is still
  counted under its home barangay. Only the relief box is given where the
  family stays.

**How the system decides**

"Staying in another barangay" means at least one member is checked in now
(`currently_evacuated`, `inside_center`) at a center whose barangay is not
the family's home barangay. If members are split across barangays, the
earliest check-in decides. A family in a private house (`outside_center`)
always gets its box from its home barangay.

A handout's `barangay_id` is the barangay that gave the box (the host).
The family keeps its home `barangay_id`.

Code: `App\Services\BoxRelief\BoxReliefService::stayingElsewhere()` (now
also returns the center), `givingBarangay()`, `familiesGivenBy()` and
`needs()`.

**For the apps**

- Host barangay: the family is in `puroks` with `from_barangay: {id, name}`,
  `purok: null`, `staying_in.other_barangay: true` and `may_give: true`.
- Home barangay: the family is only in `staying_elsewhere`, with
  `staying_in`, `gives_box` and `may_give: false`. Do not show a Give
  button for it.
- `POST /box-relief/rounds/{round}/handouts` answers 403 when the home
  barangay tries to give a box to a family staying elsewhere.

## 2. Final count submitted by an official

`POST /count-submissions` (permission `count_submissions.submit`:
barangay officials). The barangay is always the official's own.

```json
{"evacuation_event_id": 1, "note": "All centers counted."}
```

| Field | Rule |
| --- | --- |
| `evacuation_event_id` | Required, an existing event, which must be **active**. |
| `note` | Optional, up to 1000 characters. |

The numbers are not sent: the server counts the barangay's registered
families and persons at that moment, split inside/outside centers. Each
submission is a new version; CSWD validates or returns the current one.

201:

```json
{
  "success": true,
  "message": "Final count sent to CSWD for validation.",
  "data": {
    "id": 1,
    "version": 1,
    "is_current": true,
    "evacuation_event": {"id": 1, "name": "Typhoon Ofel", "status": "active"},
    "barangay": {"id": 1, "name": "Tuburan"},
    "families": 1,
    "families_inside_ec": 1,
    "families_outside_ec": 0,
    "persons": 1,
    "persons_inside_ec": 1,
    "persons_outside_ec": 0,
    "note": "All centers counted.",
    "submitted_by": {"id": 2, "name": "Official One"},
    "submitted_at": "2026-11-23T16:29:30+00:00",
    "submitted_on_behalf": false,
    "paper_ec_board_entry_id": null,
    "status": "pending",
    "validated_families": null,
    "validated_persons": null,
    "reviewed_by": null,
    "reviewed_at": null,
    "review_note": null
  }
}
```

`status` is `pending`, `validated` or `returned`. `review_note` is CSWD's
reason when it returns a count.

Errors:

| Status | When | `message` |
| --- | --- | --- |
| 422 | Same counts as the pending submission | `This count is already waiting for CSWD, and nothing has changed since it was submitted.` (`errors: null`) |
| 422 | Event monitored | `"<event>" is being monitored. Final counts opens when CSWD starts the evacuation.`, `errors.evacuation_event_id` |
| 422 | Event closed | `"<event>" is closed. A closed event is read-only.`, `errors.evacuation_event_id` |
| 422 | Account has no barangay | `Your account is not assigned to a barangay.` |
| 422 | `evacuation_event_id` missing or unknown | `errors.evacuation_event_id` |
| 403 | Not an official (CSWD, the administrator) | `You are not authorized to perform this action.` |

The submission is safe to retry without `client_ref`: a second identical
submission answers the first 422 above and creates nothing.

Reading: `GET /count-submissions?evacuation_event_id=` (an official sees
their own barangay's versions, newest first) and
`GET /count-submissions/computed?evacuation_event_id=` (the numbers the
server would submit now). When CSWD submits on the barangay's behalf, the
officials get a notification of type `count_submitted_on_behalf`
(section 7.4).

## 3. The official EC Information Board (server-generated)

Officials can already generate it. **No new endpoint was needed.** The
permissions are the ones the web Reports page uses: any staff account with
operational access may generate, and an official only for a center of
their own barangay.

### 3.1 Generate

`POST /reports/ec-information-board`

```json
{"evacuation_event_id": 1, "evacuation_center_id": 1}
```

201 (`evacuation_center` is **new** in this response; it was missing
before):

```json
{
  "success": true,
  "message": "Report generated successfully.",
  "data": {
    "id": 1,
    "evacuation_event": {"id": 1, "name": "Typhoon Ofel"},
    "evacuation_center": {"id": 1, "name": "Tuburan Barangay Hall"},
    "report_type": "ec_information_board",
    "file_format": "xlsx",
    "generated_by": "Official One",
    "generated_at": "2026-11-23T16:29:30.000000Z",
    "download_url": "https://e-likasligao.online/api/v1/reports/1/download"
  }
}
```

(The DROMIC and CDRRMO generate responses now carry
`"evacuation_center": null` too, for the same shape.)

The file is an Excel workbook of the DSWD EC Information Board for that
center and event (a practice event's file is marked "DEMO – not for
submission").

Errors:

| Status | When | `message` |
| --- | --- | --- |
| 403 | A center of another barangay | `You can only generate this report for an evacuation center in your own barangay.` |
| 422 | Center not approved | `This evacuation center was not approved, so it has no EC Information Board.` |
| 422 | Event monitored | `"<event>" is being monitored. EC Information Boards opens when CSWD starts the evacuation.` |
| 422 | Missing or unknown ids | `errors.evacuation_event_id` / `errors.evacuation_center_id` |
| 403 | The administrator | `You are not authorized to perform this action.` |

A closed event's board can still be generated.

### 3.2 Download and list

- `GET /reports/{id}/download`: the file (`Content-Disposition:
  attachment`), with the same token. 403 for a report the user may not see,
  404 when the file is gone.
- `GET /reports?per_page=20&page=1`: paginated
  `{data: [report, ...], links, meta}`. An official sees only the EC
  Information Boards of their own barangay's centers.

After the user saves the file on the device, report it with section 4.

## 4. Download logging (new)

`POST /file-downloads`: the app reports a file a user saved, shared or
printed on the device. One entry is written to the activity log (System
logs, action `file.saved`, `file.shared` or `file.printed`). Nothing about
the file's contents is kept. The web pages do not call it.

Who: officials and CSWD (`operations.access`). The administrator gets
403. Limit: 60 a minute per user. Accepts `client_ref`, so a report queued
offline is logged once. Allowed for a closed event too.

```json
{
  "file_type": "ec_information_board",
  "file_format": "xlsx",
  "action": "saved",
  "evacuation_event_id": 1,
  "barangay_id": 1,
  "report_id": 1,
  "saved_at": "2026-11-24T00:15:00+08:00",
  "device_id": "6f1c2d3e-aaaa-bbbb-cccc-123456789abc",
  "client_ref": "9a7e4c2b-1f3d-4e5a-b6c7-d8e9f0a1b2c3"
}
```

| Field | Rule |
| --- | --- |
| `file_type` | Required. A lowercase code, 2-50 characters of `a-z 0-9 _`. Known codes: `ec_information_board`, `dromic_region_v`, `cdrrmo_final`, `final_count`, `families_to_evacuate`, `relief_families`, `paper_ec_board`, `evacuees`, `map`, `other`. Another code is accepted and shown as it is. |
| `file_format` | Optional, 1-10 characters of `a-z 0-9` (`xlsx`, `pdf`, `csv`, `png`). |
| `action` | Optional: `saved` (default), `shared` or `printed`. |
| `evacuation_event_id` | Optional, an existing event. |
| `barangay_id` | Optional. Officials: left out means their own barangay; another barangay is refused (403). CSWD: any barangay, or none for a city-wide file. |
| `report_id` | Optional, a server report (section 3) the user may download, else 403. |
| `saved_at` | Required. When the user saved it on the device, ISO 8601 with the offset. Not more than 10 minutes in the future. An app sending later, after being offline, keeps the real time. |
| `device_id` | Optional, 4-100 characters of `A-Z a-z 0-9 . _ : -`. Left out: the `X-Device-Id` header. |

The platform and the version come from `X-App-Platform` and
`X-App-Version`.

201:

```json
{
  "success": true,
  "message": "File recorded in the activity log.",
  "data": {
    "id": 3,
    "action": "file.saved",
    "file_type": "ec_information_board",
    "file_format": "xlsx",
    "evacuation_event_id": 1,
    "barangay_id": 1,
    "report_id": 1,
    "saved_at": "2026-11-24T00:15:00+08:00",
    "device_id": "6f1c2d3e-aaaa-bbbb-cccc-123456789abc",
    "logged_at": "2026-11-23T16:29:59+00:00"
  }
}
```

The entry as the administrator sees it in `GET /system-logs`:

```json
{
  "id": 3,
  "user": {"id": 2, "name": "Official One"},
  "action": "file.saved",
  "action_label": "File saved (app)",
  "description": "Official One saved an EC Information Board (xlsx) for barangay Tuburan, event #1, report #1, on the mobile app 0.4.0 (device 6f1c2d3e-aaaa-bbbb-cccc-123456789abc) at Nov 24, 2026 12:15 AM.",
  "practice": false,
  "created_at": "2026-11-23T16:29:59.000000Z"
}
```

The time in the description is Philippine time. An entry about a practice
event is marked `practice: true` like every other entry.

Errors:

| Status | When | Body |
| --- | --- | --- |

## 5. Families to evacuate

A barangay's list for an event, built while the event is **monitored**
(or active). Listed families are not evacuees until checked in.
Officials manage their own barangay's list
(`families_to_evacuate.manage`); CSWD reads every barangay's.

### 5.1 Read the list

`GET /families-to-evacuate?evacuation_event_id=1` (CSWD adds
`barangay_id=`; left out, CSWD gets every barangay). Without
`evacuation_event_id`, the user's selected event.

```json
{
  "success": true,
  "message": "Request successful.",
  "data": {
    "evacuation_event": {"id": 1, "name": "Typhoon Ofel", "status": "monitoring"},
    "barangay": {"id": 1, "name": "Tuburan"},
    "summary": {"families": 2, "persons": 5, "checked_in": 0},
    "can": {"manage": true, "check_in": false},
    "families": [
      {
        "id": 1,
        "head": "Carla Santos",
        "head_first_name": "Carla",
        "head_last_name": "Santos",
        "head_sex": null,
        "members_count": 4,
        "purok": {"id": 1, "name": "Purok 2", "is_high_risk": false, "risk": null},
        "barangay": {"id": 1, "name": "Tuburan"},
        "contact_number": "09171234567",
        "note": null,
        "from_past_event": null,
        "status": "expected",
        "family_id": null,
        "checked_in_at": null

```

High-risk puroks come first, then by purok, expected before checked in,
then by name. `status` is `expected` or `checked_in`; `family_id` is the
registered family once checked in. `from_past_event` is
`{family_id, event}` for a family picked from a past event.

### 5.2 Add a family (now with client_ref)

`POST /families-to-evacuate`

A new family:

```json
{
  "evacuation_event_id": 1,
  "head_first_name": "Carla",
  "head_last_name": "Santos",
  "head_sex": "female",
  "members_count": 4,
  "purok_id": 1,
  "contact_number": "09171234567",
  "note": "Near the river",
  "client_ref": "0b6e1f2a-3c4d-4e5f-8a9b-c0d1e2f3a4b5"
}
```

A family from a past event (its head and members are taken from that
record): `{"evacuation_event_id": 1, "source_family_id": 57, "client_ref": "..."}`.
Pick it from `GET /families-to-evacuate/past-families?search=`.

| Field | Rule |
| --- | --- |
| `evacuation_event_id` | Required. Monitored or active (closed: 422). |
| `head_first_name`, `head_last_name` | Required without `source_family_id`, up to 100. |
| `head_sex` | Optional: `male`, `female`. |
| `members_count` | Optional, 1-30 (default 1). |
| `purok_id` | Optional, a purok of the official's barangay. |
| `source_family_id` | Optional: a family of the barangay from a **past** event. |
| `contact_number` | Optional, up to 30. `note`: optional, up to 255. |
| `client_ref` | Optional, a UUID. **New.** |

201: the row (as in 5.1), message `Added to your list.` Sent again with
the same `client_ref`: the same 201 and body, header
`Idempotent-Replayed: true`, still one row.

Errors: 422 `That purok is not in your barangay.` (`errors.purok_id`);
422 `Pick a family of your barangay from a past event.` and `This family
is already on your list.` (`errors.source_family_id`); 422 `That family
has no named members to reuse. Add it as a new family.`; 422
`errors.head_first_name` / `errors.head_last_name`; 422 closed event; 403
for CSWD and the administrator.

### 5.3 Change a listed family

`PATCH /families-to-evacuate/{id}` with any of `purok_id`,
`head_first_name`, `head_last_name`, `head_sex`, `members_count`,
`contact_number`, `note`. 200 with the row, message `Saved.` 422 `This
family is already checked in. Change it on the Evacuees page.`; 403
`Only the barangay that listed this family can change it.`

### 5.4 Remove a listed family

`DELETE /families-to-evacuate/{id}` (no body). 200:

```json
{"success": true, "message": "Removed from your list.", "data": null}
```

422 `A family already checked in stays on the list.` (`errors: null`); 403
`Only the barangay that listed this family can change it.` A retried
delete of a row already removed answers 404: treat it as done.

### 5.5 Check in (active only, send client_ref)

`POST /families-to-evacuate/{id}/check-in` registers the listed family
at one of the barangay's own centers, or in a private house.

At a center:

```json
{"evacuation_center_id": 1, "client_ref": "7c8d9e0f-1a2b-4c3d-9e4f-5a6b7c8d9e0f"}
```

In a private house:

```json
{"host_name": "Lito Reyes", "host_purok_id": 1, "host_address": null, "client_ref": "1d2e3f4a-5b6c-4d7e-8f9a-0b1c2d3e4f5a"}
```

201 (message `Checked in at Tuburan Barangay Hall.` or `Checked in:
staying in a private house.`): the row with `status: "checked_in"`,
`family_id`, `checked_in_at`, plus `registered_family_id`:

```json
{
  "success": true,
  "message": "Checked in at Tuburan Barangay Hall.",
  "data": {
    "id": 1, "head": "Carla Santos", "head_first_name": "Carla", "head_last_name": "Santos",
    "head_sex": null, "members_count": 4,
    "purok": {"id": 1, "name": "Purok 2", "is_high_risk": false, "risk": null},
    "barangay": {"id": 1, "name": "Tuburan"},
    "contact_number": "09171234567", "note": null, "from_past_event": null,
    "status": "checked_in", "family_id": 2, "checked_in_at": "2026-11-23T16:29:30+00:00",
    "registered_family_id": 2
  }
}
```

Errors: 422 while monitored (`"<event>" is being monitored. Checking in
listed families opens when CSWD starts the evacuation.`); 422 `This family
is already checked in.`; 422 `Choose a center, or a private house.` /
`Enter who the family stays with.`; 422 for another barangay's center
(`Check a family in at one of your own centers. To use another barangay's
center, ask for space (Transfers).`), a closed center, or one not usable;
422 `That purok is not in your barangay.` (`errors.host_purok_id`); 403
not the listing barangay.

**Who the public sees.** `/public/alerts` lists only alerts for the
whole city or for one barangay. An alert sent to one person (an
individual SMS to an evacuee) never appears there, is not counted in
`meta.total`, is never pushed, and is not sent on the realtime channel
`dashboard-alerts` (which needs no sign-in). An alert whose barangay no
longer exists is treated the same way, so it can never widen to the
whole city. One rule decides all of these:
`App\Models\Alert::isForPublicAudience()` (query form
`Alert::publicAudience()`). Staff still see every alert in `GET /alerts`.
Before November 24 (second update), one-person alerts did appear in
`/public/alerts` and on the realtime channel.

Every public endpoint was checked: `/public/evacuation-centers` (list,
one, nearest), `/public/gis/map-data`, `/public/gis/barangay-status` and
`/public/system-status` carry no alerts, and the public pages
(`/community-alerts`, `/find-evacuation-centers`, `/hotlines`) read alerts
only through `/public/alerts`. Test: `PublicAlertAudienceTest`.

## 9. What each app must change

### Mobile app (0.4.0 → next)

Barangay official:

1. **Relief boxes**: send `client_ref` with
   `POST /box-relief/rounds/{round}/handouts` (one UUID per queued give).
   Read `staying_in` and `may_give` on each family and show
   `staying_elsewhere[]` as a read-only "Staying in another barangay"
   group (no Give button). Ask before an out-of-priority give
   (section 1.3).
2. **Families to evacuate**: send `client_ref` with
   `POST /families-to-evacuate`. Treat a 404 on a retried
   `DELETE /families-to-evacuate/{id}` as done.
3. **Downloads**: after saving, sharing or printing an EC Information
   Board or any other file, call `POST /file-downloads` (queue it offline
   with a `client_ref`).
4. **EC Information Board**: use `POST /reports/ec-information-board` and
   `GET /reports/{id}/download` (no new endpoint); `evacuation_center` is
   now in the response.
5. **Notifications**: use `type` (open the EC Board on
   `registration_open`), `evacuation_event_id` and `barangay_id`.
6. **Dashboard**: map `todo[].kind` to screens and use `todo[].action` as
   the button label; show `centers[].readiness` (section 7.1).

Resident:

7. **Barangay status**: show `flood` and `mayon` (`mayon.label` and
   `mayon_zones.label`) from `GET /public/gis/barangay-status`.
8. **Alerts**: filter `GET /public/alerts` by `target_barangay`.

### Desktop app (2.1.0 → next)

1. **Relief boxes**: `client_ref` on handouts; `staying_in`, `may_give`
   and `staying_elsewhere[]`; the out-of-priority question (section 1).
2. **Families to evacuate**: `client_ref` on add.
3. **Downloads**: `POST /file-downloads` after every file the user saves,
   exports or prints (`X-App-Platform: desktop`).
4. **EC Information Board**: as for the mobile app.
5. **Notifications**: `type`, `evacuation_event_id`, `barangay_id`.
6. **Dashboard**: `todo[]` and `readiness` as above.
7. **Alerts** (staff list): `target_barangay` is available beside `target`.
