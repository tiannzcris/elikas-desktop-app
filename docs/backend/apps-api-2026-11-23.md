# API changes for the mobile and desktop apps (November 23, 2026, second update)

Every API change from the November 23 accounts and administrator work.
Paths are relative to `/api/v1`. Responses keep the usual envelope
`{success, message, data, errors}`. The list of what the apps have to
change is at the end (section 9). Section 10 adds the November 24 update:
push notifications and System logs.

## 1. Signing in

### Email or username

`POST /auth/login {email, password}` is unchanged in shape. The `email`
field now takes the account's email **or** its username. A value without
`@` is looked up as a username (case-insensitive). The barangay official
accounts made by the administrator have usernames like `brgy.tuburan`
and emails like `brgy.tuburan@e-likasligao.online`.

The user object (login, `GET /auth/me`, `GET /users`) has two new fields:

| Field | Meaning |
| --- | --- |
| `username` | `brgy.<barangay>` for those accounts, else usually `null` |
| `must_change_password` | `true` when the account is on a temporary password |

### Temporary passwords: change before anything else

An account gets a temporary password when it is created (Add user, or
"Create accounts for barangays without an official") and when the
administrator resets its password. Format: `<barangay-slug>-XXX-XXXX-XXX`
(three groups of letters and digits), e.g. `tuburan-q7K-2mPd-X4a`.

While `must_change_password` is `true`, every API call answers
**403** with `errors.code = "password_change_required"`, except:

- `GET /auth/me`
- `POST /auth/logout`
- `POST /auth/password`
- `GET /system-notices`

`POST /auth/password {current_password, password, password_confirmation}`
(any signed-in account, 10 per minute): the new password needs at least
10 characters and must differ from the current one. 422 with
`errors.current_password` when the current password is wrong. On success
it returns `{user}` (with `must_change_password: false`) and ends the
account's **other** sessions; the token used for the call stays valid.

The server can switch this rule off (`ELIKAS_REQUIRE_PASSWORD_CHANGE=false`,
for demonstrations); `must_change_password` is then always `false`.

### Locked accounts

After 5 failed sign-ins in a row the account is locked for 15 minutes:
`POST /auth/login` answers **423** with a message saying when to try
again, even with the right password. The administrator can unlock it at
once. A successful sign-in resets the count.

### Maintenance mode

When the administrator switches maintenance mode on, every signed-in call
by CSWD or a barangay official answers **503** with
`errors.code = "maintenance"` and the administrator's message in
`message` (header `Retry-After: 300`), except `GET /auth/me`,
`POST /auth/logout` and `GET /system-notices`. Signing in answers 503
too. The administrator is not affected. `api/v1/public/*` stays up.

`GET /public/system-status` (no sign-in):

```json
{
  "maintenance": {"enabled": true, "message": "Updating until 10:30 PM."},
  "app_versions": {
    "mobile": {"latest_version": "0.3.3", "latest_build": 8, "min_build": 1, "download_url": "...", "file_updated_at": "..."},
    "desktop": {"latest_version": "2.0.2", "download_url": "...", "file_updated_at": "..."}
  },
  "server_time": "2026-11-23T14:00:00+00:00"
}
```

The app versions are read from `public/downloads/version.json` and
`public/downloads/desktop-version.json` (the files uploaded with the
installers).

## 2. Device and sync headers (optional)

The server remembers the phone or computer each app request comes from,
for the administrator's "Devices and sync" view. Send these headers on
every signed-in request; all are optional and the web pages send none:

| Header | Value |
| --- | --- |
| `X-Device-Id` | A stable id the app makes once per install: 4-100 characters of `A-Z a-z 0-9 . _ : -` (a UUID works). Without it nothing is recorded. |
| `X-App-Version` | e.g. `2.0.3` |
| `X-App-Platform` | `mobile` or `desktop` |
| `X-Sync-Pending` | Records waiting on the device to be sent (a whole number) |
| `X-Sync-Failed` | Records the device could not send |
| `X-Last-Sync` | When the device last finished sending (ISO 8601) |

Nothing changes in the responses. A device seen in the last minute with
nothing new is not written again. When the administrator signs a device
out, its token stops working (401): the app should go to its sign-in
screen.

## 3. Report a problem

For CSWD and barangay officials (`support.report`); the administrator
reads and answers them.

- `POST /support-requests` (multipart): `what_happened` (10-2000
  characters, required), `page` (the screen, up to 255), `screenshot`
  (optional image: png, jpg, webp, up to 5 MB), `source`
  (`mobile`/`desktop`/`web`; defaults to `X-App-Platform`). The app
  version comes from `X-App-Version`. Answers 201 with the report. At
  most 10 reports a minute per user (429 beyond).
  Ask users not to include evacuees' names or details in the screenshot.
- `GET /support-requests/mine`: the user's reports, newest first:
  `{id, what_happened, page, source, app_version, has_screenshot, status,
  status_label, reply, replied_by, replied_at, resolved_at, created_at}`.
  `status` is `new`, `in_progress` or `resolved`.
- `GET /support-requests/{id}/screenshot`: the image (reporter and
  administrator only).

When the administrator changes the status or replies, the reporter gets
an in-app notification (`GET /notifications`) titled
`Your problem report: <status>`, with `support_request_id`.

## 4. System notices

Technical notices from the administrator (a new app version, maintenance
at 10 PM), separate from alerts. `GET /system-notices` (any signed-in
account, also during maintenance and before a password change): the
notices showing now, `[{id, title, message, starts_at, ends_at, state}]`.
Show them as a banner; there is nothing to mark as read.

## 5. Final count submitted by CSWD on behalf of a barangay

`POST /barangays/{barangay}/count-submissions` (CSWD,
`count_submissions.submit_on_behalf`):

- Barangay **without** an official account: as before
  (`{evacuation_event_id, note?}`).
- Barangay **with** an official account (new): CSWD may submit whenever it
  decides, with `{evacuation_event_id, reason, confirm: true}`. `reason`
  is required (10-500 characters). 422 with `errors.reason` or
  `errors.confirm` otherwise. The count is validated at once, its `note`
  is `Submitted by CSWD on behalf of <barangay>. Reason: <reason>`, and the
  barangay's officials get a notification titled
  `CSWD submitted the final count of <barangay>`. They can still submit an
  updated count (normal validation).

`GET /count-submissions/computed` has a new `on_behalf` object for CSWD
(guidance only, never a rule): `{has_official_account, reason_required,
last_reminded_at, officials: [{id, name, last_activity_at}]}`.

## 6. Paper EC Board encoded by CSWD (totals only)

When a barangay has no official account, or has registered no evacuees in
the event, CSWD can type in the totals from its paper EC Board. No evacuee
is created.

- `GET /barangays/{barangay}/paper-ec-board-form?evacuation_event_id=`
  (CSWD): `eligibility {allowed, why, has_official, registered_families}`,
  the barangay's `centers`, `age_brackets`, `sectoral_groups`.
- `POST /barangays/{barangay}/paper-ec-boards` (CSWD, multipart):
  `evacuation_event_id`, `reason` (10-500), `confirm=1`, `board_date?`,
  `submit_as_final_count` (default 1), `centers[i][evacuation_center_id]`
  or `centers[i][center_name]`, `centers[i][families]`,
  `centers[i][persons]`, `centers[i][age_sex][<bracket>][male|female]`,
  `centers[i][sectoral][<group>][male|female]`, and `photos[]` (1-10
  images, up to 8 MB each, required). Families cannot exceed persons, and
  the age groups cannot add up to more than the persons.
  With `submit_as_final_count`, a validated final count is made from the
  totals (`paper_ec_board_entry_id` set on it) and DROMIC reports them.
  The barangay's officials, if any, are notified.
- `GET /paper-ec-boards?evacuation_event_id=&barangay_id=` and
  `GET /paper-ec-boards/{id}`: CSWD any barangay, officials their own.
  `GET /paper-ec-boards/{id}/photos/{photo}`: the photo.
- Count submissions have a new field `paper_ec_board_entry_id` (null
  unless the count came from a paper board).

Relief for such a barangay is recorded as a total:
`POST /box-relief/rounds/{round}/total-handouts {barangay_id, boxes, note?}`
(CSWD, `box_relief.act_on_behalf`; only for a barangay whose current count
came from a paper board), and
`POST /box-relief/total-handouts/{id}/void {reason}`. These boxes count as
given in the round figures and in DROMIC.

## 7. Center locations

The center objects of the GIS endpoints (`/gis/centers/{id}`,
`/gis/center-locations`, `/gis/barangays/{id}`) have two new fields:
`location_origin` (`cswd`, `official`, `original`, or `null` without a
location) and `location_origin_label` ("Set by CSWD", "Set by barangay
official", "Original data").

## 8. Registrations

Families now record who registered them (the signed-in account). Nothing
changes for the apps; the field is not in the family resource yet.

## 10. Update of November 24: push notifications, System logs

### Push notifications for the residents' app

The server now sends push notifications through Firebase Cloud Messaging,
by topic: `elikas-city` for the whole city and `elikas-brgy-<barangay-slug>`
for each barangay (plus `elikas-test` for the administrator's test).
Pushes go out only for Emergency alerts and for Preemptive or Forced
evacuation orders, never for Advisory or Info alerts and never in a
practice event. The full description (topics, when, the payload, and what
the app must do) is in `docs/push-notifications.md`.

`GET /public/gis/barangay-status` has three new fields, so the app never
builds topic names itself:

| Field | Meaning |
| --- | --- |
| `city_push_topic` | `elikas-city` (top level) |
| `barangays[].slug` | e.g. `tula-tula-pequeno` |
| `barangays[].push_topic` | e.g. `elikas-brgy-tula-tula-pequeno` |

### System logs (administrator; desktop app if it shows them)

- `GET /system-logs` hides entries about practice events by default. New
  filter `practice`: `hide` (the default), `include` (all entries) or
  `only`. The same filter applies to `GET /system-logs/export`.
- Each entry has two new fields: `action_label` (e.g. "Relief stock
  received" for `box_relief.stock_received`; show it, with `action` as
  secondary text) and `practice` (`true` for an entry about a practice
  event: written by `demo:reset` or the practice seeders, or naming a
  practice event).
- `GET /system-logs/actions` rows have `label` next to `action` and `count`.
- Stock sources read "LGU" and "DSWD" in log descriptions, old entries
  included.
